## Ограничения
- Бюджет и сроки пилота ограничены: одна сеть, 20 мерчантов, до 100 платежей/день
- Платёжный шлюз только эмулируется (без реального эквайринга); PAN/CVV не хранятся
- Стек прототипа: Python 3 + CSV, без внешней БД; API — OpenAPI 3.0.3
- Клиент анонимен (минимальный device_id для антифрода), без полноценного личного кабинета
- Реквизиты сотрудника хранятся только маской — выплаты через токен провайдера

## Пользовательские сценарии



### Сценарий 1. Клиент оставил чаевые

1. Клиент сканирует QR на чеке → приложение вызывает GET /qr/{qr_id} 
2. Сервер проверяет подпись, TTL, nonce, merchant.status → возвращает данные чека и tip_options 
3. Клиент выбирает tip_pct (например, 5 %) → POST /tips с idempotency_key; сервер считает tip/amount_total, создаёт платёж (CREATED)
4. Клиент подтверждает → эмулятор возвращает SUCCESS → запись в payments.csv + аудит; клиент видит «Спасибо! Чаевые отправлены»



### Сценарий 2. Клиент отменил платёж

1. Клиент создал платёж (CREATED/PENDING) и нажал «Отменить» → POST /payments/{id}/cancel
2. Сервер проверяет статус: CREATED/PENDING → CANCELED (200); из SUCCESS → 409 CANCEL_NOT_ALLOWED
3. Событие payment_canceled пишется в аудит; сумма не списывается



### Сценарий 3. QR устарел

1. Клиент сканирует QR после exp → GET /qr/{qr_id} возвращает 410 QR_EXPIRED (retryable = да, новый QR)
2. Платёж не создаётся; клиент просит у официанта новый QR



### Сценарий 4 (официант). Генерация QR на чек

1. Официант в кабинете выбирает чек receipt_id → POST /qr (только свои чеки)
2. Сервер проверяет merchant.status = ACTIVE, принадлежность employee_id мерчанту, уникальность receipt_id → создаёт qr_id, nonce, exp (+24 ч), signature
3. Возвращает QR-код и ссылку https://tips.example/pay?qr={qr_id}



### Сценарий 5 (клиент). Отказ шлюза

1. Клиент подтверждает платёж → эмулятор возвращает 8 (DECLINED)
2. Платёж сохраняется со статусом DECLINED, error_code = CARD_DECLINED; клиенту — «Оплата не прошла, попробуйте другой способ» (retryable — новый QR/другой способ)
