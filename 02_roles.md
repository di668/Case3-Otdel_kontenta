## Процесс регистрации мерчанта 

|Шаг|Кто делает|Что происходит|Проверки|
|-|-|-|-|
|1|Мерчант|Заполнение регистрационной формы.|Корректность данных.|
|2|Система|Получание заявки и сохранение со статусом ожидания проверки.|Отсутствие повторной регистрации, формат и корректность данных.|
|3|Администратор|Проверка заявки, принятие решения по заявке.|Достовернность предоставленных данных, отсутствие подозрительных регистрация.|
|4|Система|При одобрении: активация учетной записи, предоставление доступа к личному кабинету. При отказе: сохранение статуса отказа.|Решение администратора. Смена статуса ACTIVE и REJECTED.|



## Процесс регистрации сотрудника 

|Шаг|Кто делает|Что происходит|
|-|-|-|
|1|Мерчант|Добавление нового сотрудника, указание имени и контактных данных, отправление приглашения.|
|2|Система|Создание приглашения, связка будущей учетной записи с merchant_id.|
|3|Официант|Принятие приглашения, регистрация, подтверждение данных. Указание реквизитов для получения выплат.|
|4|Система|Проверка приглашения, сохранение данных, предоставление доступа к личному кабинету. Сохранение и маскировка платежных реквизитов.|


## Процесс регистрации клиента

* Регистрация не требуется.

## Критерий приёмки

- [ ] Все 4 роли описаны
- [ ] Матрица прав заполнена (8 действий × 4 роли)
- [ ] Регистрация мерчанта: 4 шага с проверками
- [ ] Регистрация сотрудника: 3–4 шага
- [ ] Реквизиты сотрудника маскируются (\*\*\*\*1234), не хранятся открыто
- [ ] Клиент может сканировать QR только своего чека (привязка к receipt\_id)



## Подсказки

- Мерчант не может сам себя активировать — нужен администратор.
- Официант не может видеть чаевые коллег — только свои.
- Клиент анонимен (или имеет минимальный профиль), но нужен для антифрода.
- Реквизиты (карта/счёт) — только для выплат, не для оплаты клиентом.
